## 2026-11-02 morning: harnesslag (reusing stale-harness rollouts in agent RL with a per-source mismatch correction)
Status: proposed, needs Sebastian's go before a cloud agent starts.
Hashtags (GitHub topics, also shown in the README): #ai-frontier-research #llm-agents #reinforcement-learning #grpo #agent-harness #importance-sampling #off-policy-rl #qwen
Signals combined: harness and policy co-evolution (rsi-harness 0.55, strengthened today; harness evolution now also in robot agents, agents-for-robots 0.5), RL train-inference mismatch decomposed by source (new today, 0.4).

Idea: In harness-policy co-evolution RL the harness (system prompt, tool-output format, reminders, retry hooks) changes during training. Every rollout collected under an older harness version is then off-policy in a new way that existing corrections do not see: the policy weights may be almost the same, but the context the tokens were sampled in is different. Current practice throws those rollouts away (CoTrace restricts RL to fresh interactions) or reuses them as is. harnesslag stores each rollout as its underlying environment trace (actions plus raw tool results), re-renders it under the current harness, and splits each token's log-ratio exactly into three terms: engine numerics (trainer vs sampler at the sampler's weights and context), policy lag (old vs current weights, old context) and harness lag (current weights, new vs old rendering). Following the finding that numerics are a near-constant bias while lag grows, numerics are centered, and the two lag terms get separate truncated importance weights. Edits that change tool semantics (not just rendering) make a trajectory non-renderable and it is dropped. The output is an RL algorithm that keeps learning from stale-harness data instead of discarding it.

Why it is new (closest prior work, checked on arXiv, HF papers and GitHub on 2026-11-02):
- On the Origin and Evolution of Training-Inference Mismatch in LLM RL (https://huggingface.co/papers/2610.40945): exact split into engine numerics and policy lag with per-source corrections; no harness or context term, single fixed prompt.
- bf16 Rounding Silently Discards Most RL Policy Updates (https://arxiv.org/abs/2610.41073v1) and CIS (https://arxiv.org/abs/2609.32444v1): numerical and lag mismatch fixes; same context on both sides.
- CoTrace (https://arxiv.org/abs/2610.10426v1): harness-aware data routing that conditions RL on fresh interactions under the adopted runtime; it avoids reuse, it does not correct it.
- HarnessAdapt-RL (https://arxiv.org/abs/2610.28069v1), Self-HPO (https://arxiv.org/abs/2610.22791v1), WHALE (https://arxiv.org/abs/2609.00196v1), HarnessForge (https://arxiv.org/abs/2606.01779v1), CoEvo-RSI (https://arxiv.org/abs/2610.25078v1): alternate or co-train harness and policy; none of the abstracts describes importance correction or re-rendering of rollouts across harness versions.
- MemoryWalker (https://arxiv.org/abs/2609.00865v1): train-inference mismatch from context compression inside one harness (exact tree corrections); not harness version changes.
- Evolving Together, Failing Apart (https://arxiv.org/abs/2610.20845v1): shows co-evolved policies are fragile to skill-bank drift; an evaluation protocol, not a training correction.
- arXiv searches (harness + importance sampling, harness version + RL, harness-aware off-policy, context mismatch + GRPO, system prompt + off-policy + GRPO) found nothing on this; GitHub searches (harness importance sampling grpo, harness lag rl, harness co-evolution rl replay, prompt change importance sampling grpo) returned 0 repos.

Hypothesis (falsifiable): in GRPO with an evolving harness on a tool-using math agent, harnesslag reaches the final GSM8K test accuracy of the discard-stale baseline with at least 25% fewer fresh rollouts, and beats naive reuse (old context, no correction) by at least 2 points at equal fresh rollouts. The harness-lag term should spike at harness edits and exceed the numerics term there. Fails if the rollout saving is under 10% or inside 3-seed variance, or if re-rendering without importance weights (arm C) matches it (then the correction is unnecessary, which is itself a reportable result).

Experiment (real runs only):
1. Policy: Qwen2.5-0.5B-Instruct (Apache-2.0); smoke and CPU checks with SmolLM2-135M-Instruct (Apache-2.0).
2. Task: GSM8K (MIT) with a Python calculator tool, 3 tool turns max; train split for RL, 200 held-out train problems for harness selection, the full 1,319-problem test split for reporting.
3. Harness evolution inside the run: every 25 RL steps, propose 4 single-component edits from a real component space (3 system prompts, tool-output format raw / truncated / JSON, error reminder on or off, answer-format reminder on or off, plus one semantic edit: calculator rounding to 2 decimals, which is not re-renderable). Accept the best edit only if a paired test on the selection split passes (p < 0.1), as TinyAstral does.
4. Arms at matched fresh rollouts and optimizer steps: (A) discard stale rollouts, (B) naive reuse in old context, (C) re-render without importance weights, (D) harnesslag, (E) re-render with one combined truncated IS cap (no decomposition). Replay buffer holds the last 4 batches. 3 seeds each, about 150 RL steps, 8 samples per prompt.
5. Report: test accuracy vs fresh rollouts, final test accuracy with 95% CIs, per-source mismatch magnitudes over training with harness-edit markers, share of stale tokens clipped, accepted harness edits per seed, GPU-hours, every run including failed or negative ones.

Key files (ponytail: fewest files): `harnesslag/harness.py` (component space and deterministic render of an env trace), `harnesslag/env.py` (GSM8K tool env, stores raw traces), `harnesslag/mismatch.py` (exact 3-term log-ratio split, centering, per-source truncated IS), `harnesslag/train.py` (plain PyTorch GRPO loop with replay buffer and arm flag), `harnesslag/evolve.py` (edit proposals and paired-test acceptance), `scripts/plots.py` and `scripts/demo_gif.py` (charts and GIF from results), `results/` (real run logs and JSON only), `test_harnesslag.py` (one file).

How to verify: `python3 test_harnesslag.py` runs on CPU with 16 real GSM8K problems and SmolLM2-135M-Instruct: it checks that the three terms sum to the total log-ratio within 1e-4, that rendering a trace under harness v1 then v2 then v1 is byte-identical, that semantic edits mark traces non-renderable, and runs one RL step per arm. `make repro ARM=D SEED=0` reproduces a single run; README tables and charts are regenerated from `results/*.json` by `scripts/plots.py`.
